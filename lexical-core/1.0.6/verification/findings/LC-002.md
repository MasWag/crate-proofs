## Expected behavior and its basis

A configured suffix `h` can be consumed as part of a number; it does not make `?` a suffix. Per the release documentation, partial parsing stops when an invalid digit is found and complete parsing errors on invalid digits. For `b"12?x"`, the expected partial result is `Ok((12, 2))`, with `b"?x"` residual input, and the complete result is `Err(InvalidDigit(2))`. See the [release API documentation](https://docs.rs/lexical-core/1.0.6/lexical_core/fn.parse_partial_with_options.html) and unchanged facade `src/lib.rs:1149-1175`. The examples use a valid format built with `build_strict()` and a built-in integer type.

## Observed behavior

`parse_partial_with_options::<u8, FORMAT>(b"12?x", ...)` returns `Ok((12, 3))`, implying residual `b"x"`. Complete parsing returns `Err(InvalidDigit(3))`. First discrepancy: cursor advancement at an unrelated invalid byte with following input. Controls pass for partial `b"12?"` consuming two bytes and `b"12h?"` consuming three.

## Cause, impact and proof scope

Source review: the `fmt_invalid_digit!` macro at `lexical-parse-integer/src/algorithm.rs:135-157` advances the iterator in its nonempty-buffer branch without requiring `is_suffix`. Both partial length and complete error position use that cursor. The lexical-core facade forwards directly to the dependency.

The observation concerns custom integer formats. It is not evidence about standard integer formats, float parsing, writing, other integer widths or targets. Forwarding correctness can hold while the delegated numeric parser has this behavior. Any correctness claim about the facade's result must account for the dependency's actual semantics; it cannot follow merely from forwarding. Formal proof work and any resulting contract exclusions are documented separately in the version's coverage ledger.
