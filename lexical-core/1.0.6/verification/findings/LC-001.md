## Expected behavior and its basis

A single zero is a valid integer even when leading zeros are forbidden. Partial parsing of `b"0"` should consume one byte, and signed `b"-0"` should consume two. The release partial-parser documentation says parsing continues until an invalid digit or end of input; its examples return the byte offset delimiting the parsed number. See the [release API documentation](https://docs.rs/lexical-core/1.0.6/lexical_core/fn.parse_partial_with_options.html) and unchanged facade `src/lib.rs:1149-1175`. The examples use a valid format built with `build_strict()` and a built-in integer type.

## Observed behavior

`parse_partial_with_options::<u8, FORMAT>(b"0", ...)` returns `Ok((0, 0))`. The signed i8 call on `b"-0"` returns `Ok((0, 1))`. The residual input implied by each returned offset still contains the parsed zero. First discrepancy: the returned cursor on the single-zero end-of-input path. Controls pass for standard `b"0"`, custom-format complete `b"0"`, partial `b"0!"`, and rejection of `b"01"`.

## Cause, impact and proof scope

Source review: `lexical-parse-integer/src/algorithm.rs:657-671` skips the zero, computes `index = iter.cursor() - zeros`, then returns `index` on end of input. This is the pre-zero offset. The lexical-core facade forwards directly to the dependency.

The observation concerns custom integer formats. It is not evidence about standard integer formats, float parsing, writing, other integer widths or targets. Forwarding correctness can hold while the delegated numeric parser has this behavior. Any correctness claim about the facade's result must account for the dependency's actual semantics; it cannot follow merely from forwarding. Formal proof work and any resulting contract exclusions are documented separately in the version's coverage ledger.
