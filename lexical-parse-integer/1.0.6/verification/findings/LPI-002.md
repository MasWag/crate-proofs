# LPI-002: An unrelated byte is consumed in a suffix format

## Identity and classification

- Crate/version: `lexical-parse-integer` 1.0.6
- Component: release implementation; kind: implementation bug
- Confidence: reproduced at pinned inputs; resolution: open
- First observed / last reproduced: 2026-11-05
- Upstream report: unknown; upstream fix: not checked

## Expected behavior and its basis

Partial parsing returns the parsed value and number of bytes consumed; a configured suffix `h` does not make `?` a suffix. Complete parsing should report the first invalid byte, at index 2 in `b"12?x"`.

## Observed behavior

For `b"12?x"`, partial parsing returns `Ok((12, 3))` rather than `Ok((12, 2))`, and complete parsing returns `Err(InvalidDigit(3))` rather than `Err(InvalidDigit(2))`. Controls include `b"12?"`, which consumes two bytes, and `b"12h?"`, which consumes three.

## Evidence and interpretation

These are native observations, not formal theorems. An issue search did not identify an exact match; this does not establish novelty or upstream status.

## Cause, impact and proof scope

The suffix handling path advances past an unrelated byte when another byte follows it. The resulting cursor affects both partial consumption and the complete parse's invalid-digit position. This custom-format observation does not establish or refute the standard-format obligations in [SPECIFICATION.md](../../SPECIFICATION.md).

## Resolution and regression

The ignored assertions retain regression expectations; no fix was applied or tested.

## Issue-ready draft

Title: Suffix format advances past an unrelated invalid byte

## Description

With a base suffix configured, `from_lexical_partial_with_options` can count an unrelated invalid byte as consumed. `from_lexical_with_options` can consequently report the next byte as the invalid digit.

## Prerequisites

- Rust version: 1.94.1
- lexical-parse-integer version: 1.0.6
- Features: `format`, `power-of-two`
- Direct dependency: `lexical-util` 1.0.7 with `format` and `power-of-two`

## Test case

```rust
use core::num::NonZeroU8;
use lexical_parse_integer::{FromLexicalWithOptions, Options};
use lexical_util::format::NumberFormatBuilder;

fn main() {
    const FORMAT: u128 = NumberFormatBuilder::new()
        .base_suffix(NonZeroU8::new(b'h')).build_strict();
    let result = u8::from_lexical_partial_with_options::<FORMAT>(b"12?x", &Options::new());
    assert_eq!(result, Ok((12, 2))); // actual: Ok((12, 3))
}
```

## Additional Context

For the same input, complete parsing returns `InvalidDigit(3)` instead of `InvalidDigit(2)`. The configured suffix is `h`, not `?`.
