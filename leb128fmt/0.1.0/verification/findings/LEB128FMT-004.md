# LEB128FMT-004: Decoders mishandle continuation at width seven

## Identity and classification

- Component: release implementation; kind: implementation-bug; confidence: reproduced-at-pinned-inputs; resolution: open.
- Crate/version: leb128fmt/0.1.0; first observed and last reproduced: 2026-11-28; upstream report: not-reported; upstream fix: not-checked.

## Pinned inputs

`source.lock.json` SHA-256 `de198d9bfda1cf725813d9957bdd96c275cee7885d1b8f0e474be7749b345609`; release archive SHA-256 `09edd9e8b54e49e587e4f6295a7d29c3ea94d469cb40ab8ca70b288248a81db2`; `src/lib.rs` SHA-256 `d3416930498758a653a176d50658540adf1c81cd1e5eade97272b4df69ae92cc`. The maintained test instantiates `decode_uint_arr!` with `u32` and width 7.

## Expected and observed behavior

`[0x80]` has no terminating byte and should return `None` as an incorrect encoding. Instead the call panics at index 1 of an array of length 1. A valid terminal `[0x7f]` returns `Some((127, 1))` in the retained control. Separately, `decode_uint_slice::<u16, 7>` and `decode_sint_slice::<i16, 7>` both return `Ok(127)` and advance the cursor from 0 to 2 on `[0xff, 0x00]`. Both consume more than the single allowed group; the signed result is also outside the signed seven-bit range -64–63.

## Cause, impact and resolution

For widths divisible by seven the final-group check is delayed by one group. The array decoder reads the next array element before checking whether it exists; the slice decoders can consume that extra group. No fix or upstream contact is recorded.
