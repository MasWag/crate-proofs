# LEB128FMT-007: Primitive conversion extraction conflicts with error model

## Identity and classification

- Component: Aeneas Lean backend / extraction composition; kind: tool-defect; confidence: reproduced-at-pinned-inputs; resolution: workaround.
- Crate/version: leb128fmt/0.1.0; observed: 2026-11-28; upstream report: not-reported; upstream fix: not-checked.
- Inputs: `source.lock.json` and `aeneas/profiles/default/toolchain.lock.json`; Aeneas revision `be86ab0f1989d04944292b345b24c435be3ad10a`, unpatched.

## Expected and observed behavior

An extraction selecting concrete primitive conversion bodies should produce Lean definitions with consistent error types. For the examined selection, Lean reports `IntErrorKind.PosOverflow` or `NegOverflow` where `TryFromIntError` is expected. The pinned backend defines `TryFromIntError` as `Unit`, whereas the selected Rust representation contains an `IntErrorKind`. This blocks typechecking that combined generated module; it does not by itself establish an error in the crate. A smaller selection of unsigned `u8` writers and primitive readers compiled independently, so this is not a failure of every slice extraction.

## Evidence and scope

From the repository root, `bash leb128fmt/0.1.0/scripts/verify.sh --offline` runs the maintained `scripts/check-slice-conversion-boundary.sh`, which invokes `scripts/extract-slice-instantiations.sh all` and an optimized MIR variant. In accepted run `default-ihst5ql8`, the local-only `probe-slice-conversions/` and `probe-slice-conversions-optimized/` directories each contain `charon.log`, `aeneas.log`, generated `SliceConcrete.lean`, and `lean.log`; each reports 13 Lean type mismatches. The maintained `extraction-slices.json` selection of `u8` writers and primitive readers typechecks using unmodified Aeneas.

An exploratory fixed-width `u16`/`i16` monomorphization with optimized MIR and optimization level 3, both with and without `-filter-trait-methods`, stopped earlier at an unexpected `TSlice` symbolic expansion in Aeneas. Its local-only logs are in `.work/slice-monomorphic-1795852365/`; this is not an accepted substitute for the failed combined selection. No fix or upstream contact is recorded.


## 2026-11-28 update: scoped writer adapter

The original combined extraction failure remains reproducible and no general backend fix is claimed. The selected concrete writer proofs now use stock split-file extraction plus the target-local `aeneas/profiles/default/proofs/ConcreteWriters/FunsExternal.lean`. Its scoped coercion erases the generated `IntErrorKind` payload to the backend's unit error model. The proofs establish that conversion of each masked payload in `0..127` succeeds and preserves its value, so the erased error payload is not observed on the claimed paths. The same file forwards the length helper to a separately generated release `max_len` body, with a checked equality. Neither the release nor generated files nor Aeneas/Charon are modified. Correspondence of the translation and this boundary to Rust remains a model assumption.

The maintained `scripts/check-concrete-writer-models.sh` regenerates and compares the selected generated files; the final run and its archived evidence supply exact identity and results. This is a workaround for these selected contracts, not a resolution of arbitrary failing extractions.
