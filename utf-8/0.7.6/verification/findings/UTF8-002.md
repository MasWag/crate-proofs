# UTF8-002: Retry after a second buffer fill error can skip input

## Identity and classification

- Crate/version: `utf-8` 0.7.6; component: release implementation
- Kind: specification question; confidence: reproduced; resolution: open
- First observed and last reproduced: 2026-11-27
- Upstream report: not reported; upstream fix: not checked

## Inputs and basis

The release `src/read.rs` used in the run had SHA-256
`6eae22954e18a5afa8f62c876498a643563c5b68d03329a417aa354a28108046`.
The rustc 1.91.0 (f8297e351) run used `aarch64-apple-darwin` and default
unoptimized compilation. `source.lock.json` has SHA-256
`3e219fec23ba26a5f29e258e985055699932e1ffa2d99ec942c58920d413028b`;
the registry archive checksum is
`09cc8ee72d2a9becf2f2febe0205bbed8fc6615b7cb429ad062dc7b7ddd036a9`.
The standard [`BufRead` documentation](https://doc.rust-lang.org/std/io/trait.BufRead.html#tymethod.fill_buf)
describes `fill_buf` errors and `consume` as marking bytes read. The crate
does not explicitly specify recovery after an I/O error, so whether retry must
preserve input is a question rather than a documented contract violation.

## Observation and reproduction

The retained custom reader exposes one byte `x`, returns `Interrupted` on its
second fill, and exposes `x` again until consumed. Direct calls confirm those
three results without a consume. Through `BufReadDecoder`, the first
`next_strict` returns the I/O error and the second returns `None`, losing the
byte. This does not establish the same behavior for `std::io::BufReader`.

Reproducer: `verification/repro/bufread-retry.rs`, SHA-256
`336db4eda9b9a43c0222f59c5779cc2c8308ea9fdb2b0d3698fa46f58220ad4a`.
From the repository root, after building the release rlib as in UTF8-001:

```sh
rustc +1.91.0 utf-8/0.7.6/verification/repro/bufread-retry.rs --extern utf8=/private/tmp/libutf8-report-retained.rlib -o /private/tmp/utf8-retry-retained
/private/tmp/utf8-retry-retained
```

The program exited 0; its assertions check the direct reader, first decoder
error, and `None` on retry. Success reproduces the discrepancy. The rlib is
built by the first command in UTF8-001. This is a
native observation, not a formal proof.

## Interpretation and status

Source review shows the decoder sets its delayed consumption count before
the second fallible `fill_buf`. After the error, a retry applies that count.
This finding concerns a custom reader with a transient second-fill error;
ordinary cached-reader behavior and all other errors are not established by
this example. No fix has been tested or reported upstream.
